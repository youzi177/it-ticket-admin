# 内部 IT 报修工单 Admin 系统设计文档

- 日期：2026-11-11
- 项目代号：`it-ticket-admin`
- 状态：已定稿，待批准

## 1. 意图与背景

写作者是开发人员，没有做过产品，想做一个尽量简单的 admin 产品，用来验证「用 AI 开发产品」的完整流程：想法 → 设计 → 计划 → 实现 → 集成。产品本身是载体，不是目的。

业务域刻意选择无聊、边界清楚的「内部 IT 报修工单」，让验证的重点落在开发流程上，而不是业务逻辑上。

## 2. 目标

1. 一个可真实使用的最小 admin 系统：登录、角色权限、工单全生命周期。
2. 三种角色（员工 / 处理人 / 管理员）的权限边界清晰、可验证。
3. 全程按 Git Flow 开发（`main` / `develop` / `feature/*` / `release/*` / `hotfix/*`）。
4. 配套文档齐全（见第 12 节），任何人（或 AI）可按文档从零初始化项目并继续开发。

## 3. 非目标

- 不做：附件上传、消息通知、工单评价、优先级、分类/标签、搜索、统计报表。
- 不做：自助注册、找回密码、第三方登录（账号由管理员创建）。
- 不做：多租户、国际化、移动端专属适配。
- 不做：细粒度权限（按钮级/资源级），只做角色级 RBAC。

## 4. 反目标（做了即视为失败）

- 范围膨胀成「通用工单平台」（自定义表单、工作流引擎等）。
- 引入微服务、消息队列、事件总线等超出验证需要的复杂度。
- 业务逻辑复杂度超过流程验证所需，喧宾夺主。
- 在华丽 UI/动效上投入过多，挤占流程验证的精力。

## 5. 用户与角色

| 角色 | 说明 | 典型动作 |
|---|---|---|
| 员工 `employee` | 提交报修的人 | 提交工单、查看自己的工单、追加备注、确认关闭 |
| 处理人 `agent` | 处理报修的 IT 人员 | 接单、更新处理进度、标记完成 |
| 管理员 `admin` | 系统管理者 | 用户管理、查看/分派/关闭全部工单 |

- 一个用户只有一个角色，避免多角色组合权限（我的简化决定）。
- 账号由管理员创建，无自助注册。
- 删除用户 = 停用（软删除）：用户记录永久保留以支撑操作记录，不做硬删除（用户确认）。
- 作为处理人名下有未关闭（非 `closed`）工单的用户，不能停用或降级；必须先把这些工单改派给其他处理人，否则拒绝操作（用户确认）。

## 6. 工单生命周期

`提交 → 受理 → 处理 → 完成 → 关闭`，状态单向流转，不允许回退；关闭只能从「完成」发起，管理员也不能跳过状态（用户确认）。

| 状态 | 触发者 | 动作 |
|---|---|---|
| `submitted` 提交 | 员工 | 创建工单 |
| `accepted` 受理 | 处理人 | 接单 |
| `processing` 处理 | 处理人 | 开始处理 |
| `resolved` 完成 | 处理人 | 标记完成 |
| `closed` 关闭 | 员工（确认）或管理员 | 关闭工单（管理员不限工单归属） |

- 每次状态变更和备注都写入操作记录（时间线），不可修改、不可删除。

### 6.1 接单与分派（用户确认）

- 「待接单」= `submitted` 且处理人为空的工单，任何处理人可自助接单，接单后成为处理人。
- 管理员可对任何未关闭工单分派/改派：只更换处理人、不改变状态、写入时间线，操作权立即切换给新处理人。
- 已分派的 `submitted` 工单，由被分派的处理人接单后进入 `accepted`。
- 工单进入 `accepted` 后不允许清空处理人，只能改派给另一位处理人；`submitted` 未接单前管理员可清空处理人，退回「待接单」。

## 7. 功能范围（页面级）

1. **登录页**：账号密码登录，登录后进入工单列表。
2. **工单列表**：按角色控制可见范围，支持按状态筛选。
3. **工单详情**：字段 + 操作记录时间线 + 按角色/状态显示的操作按钮。
4. **创建工单**：填写标题、描述。
5. **用户管理**（仅管理员）：用户创建/编辑/查询、设置角色、重置密码、停用/恢复。

工单字段（最小集）：标题、描述、状态、创建人、处理人（可空）、创建时间、更新时间、操作记录。

## 8. 权限矩阵

| 功能 | 员工 | 处理人 | 管理员 |
|---|---|---|---|
| 创建工单 | ✓ | ✓ | ✓ |
| 查看工单 | 自己创建的 | 自己创建的 + 待接单的 + 自己处理的 | 全部 |
| 追加备注 | 自己创建的 | 自己处理的 | 全部 |
| 接单 | — | ✓（「待接单」或分派给自己的 `submitted` 单） | — |
| 分派/改派 | — | — | ✓（任意未关闭工单） |
| 标记完成 | — | ✓ | — |
| 确认关闭 | 自己创建的 `resolved` 单 | — | ✓（任意工单的 `resolved` 单） |
| 用户管理 | — | — | ✓（含停用/恢复） |

## 9. 约束

- 技术栈（用户定）：前端 Vue 3，后端 NestJS，数据库 MySQL。
- 文档一律 Markdown 格式（用户定）。
- 开发流程用 Git Flow（用户定）。
- 遵守项目 AGENTS.md 工程约定：目录 kebab-case、组件 PascalCase、函数 camelCase、命名导出优先、`const` 优先、early return、单文件 ≤ 300 行、注释只解释「为什么」、密钥统一走环境变量、修改后构建 + lint 无报错。
- 本地开发运行即可，暂不要求部署到服务器（我的决定）。

## 10. 用户已定的决定

1. 产品形态：admin 后台，业务域为内部 IT 报修工单（候选方案 1）。
2. 技术栈：Vue 3 + NestJS + MySQL。
3. 三种角色：员工 / 处理人 / 管理员。
4. 生命周期：提交 → 受理 → 处理 → 完成 → 关闭；工单字段取最小集（标题、描述、状态、处理人、操作记录）。
5. 交付文档：需求/设计文档、项目初始化技术文档、实施计划文档，均为 Markdown。
6. 开发模式：Git Flow。
7. 状态机为纯链式，关闭只能从「完成」发起；管理员可关闭任意工单，但不能跳过状态。
8. 接单/分派/改派规则见 6.1（含「不允许清空处理人」的边界）。
9. 用户只停用不硬删；处理人名下有未关闭工单时禁止停用/降级，先改派（见第 5 节）。
10. 仓库根目录：`/Users/bamboo/Documents/CodeProject/it-ticket-admin/`，文档统一放 `doc/`。
